# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Frontend-only workflow: `npm run dev` (`PORT=<n>` picks a private port; see `dev/serve.mjs`, README "Frontend development"). The production build uses tup (`static/Tupfile`). `npm run dev` writes generated, untracked files (`static/js/st/song_parser_peg.js`, `static/js/st/staff_assets.jsx`, `static/guides/*.json`); never commit them.
- `npm test` (`dev/run_specs.mjs`) runs the Jasmine specs bundled at `/dev/specs.html` headlessly via puppeteer and exits non-zero on any failure; CI's `node` job in `.github/workflows/test.yml` runs `make lint_js`, `npm run build_assets`, then `npm test` alongside the existing Docker Lua job.
- Lint JS with `make lint_js` (eslint over every tracked `static/js` file; it currently passes clean, so any error is yours).
- Browser data (imported pieces, practice records, practice sessions) lives in the IndexedDB local store `static/js/st/storage.js`; `initStorage()` runs in `static/js/st/app.jsx` before the app renders. Reads are synchronous over its cache (generators and settings inputs read on every render); mutations are async and write the database before the cache. Two things are never cached and are read async: each piece's source MusicXML (the uncompressed text of the imported file, `.mxl` included, gzipped in the `pieceSources` store; `pieceSource` is null for pieces imported before sources were kept) and the review log (`reviews`). Specs use `openTestStore` from `static/js/spec/helpers.js`, never the real database.
- Practice records are the spaced repetition records of `static/js/st/srs/records.js` (shapes, ids and validation there): `items` (a measure range of one piece per hand setting, id `${pieceId}:${hand}:${start}-${end}`, lifetime totals kept verbatim), the append-only `reviews` log keyed `[itemId, at]` (so a library merge is a union; `staffMisses` splits an attempt's misses by score staff) and per-piece `studies` (room for a phrase map). Write an attempt with `recordAttempt` (review, item, related items and session in one transaction; pass a function of the store to build from the item as stored); `recordSectionPractice` only adds totals to a tracked item and writes no review. `recordAttempt` also schedules a single-measure item (any hand) from each graded review in the same write (`applyGrade` in `static/js/st/srs/schedule.js`: the in-session ladder, then FSRS-6 due dates from `st/srs/fsrs.js`, checked against the `ts-fsrs` dev dependency, on local days starting 4 am); a card's range is logged but stays `tracked`. The schedule must stay what `replay(reviews)` rebuilds from the log, so change it only through `applyGrade` and bump `SCHEDULER_ALGO`. The scheduler and practice settings are `meta` records (`schedulerSettings()`, `practiceSettings()`), written with a one-time replay of measures graded before the scheduler (`setUpScheduler`). `sectionStats()` is a view over items (every hand of a range added up); the `sectionStats` store is frozen since `DB_VERSION` 4 (its rows migrated to tracked items plus `legacy` reviews), so never write it. `MemoryBackend` mirrors IndexedDB's key order and index reads, so both backends must pass the same specs.
- The UI follows the "Salon de Chopin" design spec in `docs/design/salon-de-chopin.md`: use the `--salon-*` and `--font-display` tokens in `static/js/st/global.css` and the primitives in `static/js/st/components/salon.jsx` rather than raw values. The header is fixed; offset content with `var(--header-height)`, never a hard-coded height.
- Imported sheet music is practised on its own page, `/sheet-music` (`static/js/st/components/pages/score_page.jsx`), which is the same trainer class as the exercises page (`sight_reading_page.jsx`) driven by a different `programme` prop (`SCORE_PROGRAMME` vs `EXERCISES_PROGRAMME`: generators, drawer, staff/key sources, storage key, titles). Put page differences in the programme, never a copy of the trainer. The "sheet music" generator is `SHEET_MUSIC_GENERATOR`, kept out of `GENERATORS`; the score page's mode and speed live under `SCORE_DRILL_STORAGE_KEY`, and its staff follows the piece (`scoreStaff`). A piece is practised in one of two modes, the sheet music setting `practice`: free practice (the drawer's section, cards and order) or today's programme (`plannedPractice` in `data.jsx`: offered for any imported piece, the default while it has a study, which its first programme card creates). The programme is `PlanGenerator`/`PlanDeck` (`static/js/st/plan_cards.js`), a `MeasureCardGenerator` over the whole piece whose next card comes from the pure planner `static/js/st/srs/planner.js` (single measures only; the queue is rebuilt from the items after every card, nothing is stored, so a reload resumes it; each measure is played in a card anchored on it by `anchoredCard`; the off-schedule rule of every measure card pass, below, keeps a ladder measure played before its rung is due, as the last entry or a neighbour, from climbing); the trainer shows it through optional generator hooks (`statusLine`, `caption`, `cardLabel`, `sectionLabel`) and the programme's `Preface` (the "Tonight's programme" plate, `programme_plate.jsx`).
- Engraving engines (OpenSheetMusicDisplay, BSD, and Verovio, LGPL; exact pins in `package.json`) draw a piece's source MusicXML behind one contract, `renderCard({musicXML, fromMeasure, toMeasure, hand, width})` → `{svg, notes}` (and `renderSystem`, the same range on one line with no width), in `static/js/st/score_render/` (TypeScript, compiled by esbuild, no type checking); measures are printed bar numbers (`measureNumbersFor` in `static/js/st/measure_numbers.js`, shared with the importer so a number names the same bars in both), and one hand alone is the shared MusicXML transform in `card_source.ts`, not an engine option (the score page draws the staves its drill's tracks read, `staves` from each parsed track's `scoreStaff`, so a score with a part per hand draws only the judged hand). `/score-engines` (`score_engines_page.jsx`) compares them side by side; the score page draws its cards with the programme's `engine` (`SCORE_PROGRAMME.engine`, OSMD) through `ScoreCard` (`static/js/st/components/score_card.jsx`), passing the song's `metadata.measureStarts` so drawn onsets share the columns' clock. `joinCard` (`score_render/card_join.ts`) joins the drawn heads to `extractSectionColumns`' columns by pitch and onset (tied heads with their note), and the drill only toggles `MARK_CLASSES` on them; detection, advancing and stats stay on the columns (`st/note_matcher`), each column copy carrying its `cardIndex`. In scroll mode `ScoreCard` draws the whole section as one `renderSystem` line and the scroll slider only translates it (`setOffset`): `score_render/card_scroll.ts` places each column at its joined heads (interpolating one with none by beat) and turns drawn gaps into slider units (`scrollAdvance`, used by the trainer's `columnAdvance`), so cards change by re-joining, never redrawing. The engine is the one renderer of an imported score: a piece without a stored source and an engine failure (each with its plate note, `MISSING_ENGINE_SOURCE`/`FAILED_ENGINE_SOURCE`) fall back to the app staff's plain whole note columns in both modes, the same cards either way. Detection covers the whole keyboard while the engine draws a piece, since it draws every note of the source regardless of a staff's own range: `SightReadingPage#columnStaff` feeds `pieceSection`/`pieceSectionMeasures` (`data.jsx`) an unfiltered range whenever `engineCards()` is true, rebuilding the columns when that changes. Only the app staff's fallback still clips a section to the staff's own range (the grand staff's C2–C6), and there a press of any pitch dropped anywhere in the section (`sectionDroppedPitches` in `data.jsx`) is ignored outright by `SightReadingPage#droppedStaffNote` — neither required nor a wrong key; a pitch absent from the whole section still counts as one. Specs of the app staff on the score page pass `{...SCORE_PROGRAMME, engine: null}`. Loading rule: the engines are their own ES module entry (`score_engines.js`, built by `dev/esbuild_options.mjs` and `static/Tupfile`) fetched on demand through `loadScoreEngines` (`score_render/load.js`); never import them statically into the app bundle, and serve Verovio's `verovio-module.mjs`/`verovio.mjs` unmodified as separate files beside that bundle (LGPL).
- Staff mode generators live in the `GENERATORS` registry in `static/js/st/data.jsx`; the trainer's programme drawer (`ProgrammeDrawer` in `static/js/st/components/sight_reading/settings_panel.jsx`) renders their declarative `inputs`. The trainer's programme (staff, generator, key, mode, scroll speed) is stored under `DRILL_STORAGE_KEY` through the helpers in `static/js/st/generators.js`: the `/setup` page (`setup_page.jsx`) writes it and the trainer reads it at mount, so add new programme fields there, not in component state alone. Page actions that belong in the fixed header's top row portal into `HEADER_ACTIONS_ID` (`static/js/st/components/header.jsx`).
- Sheet music measure flashcards (card grouping, in order/weakest-first random picks: `cardWeights` is the mean `practiceWeight` of each card's measure items under the drawer's hand, `1 + 4·(1 − R) + recentMissRate`, at least 2 while learning or relearning) live in `static/js/st/measure_cards.js`, wired up by `measureCardDeck` in `data.jsx`. Score practice is recorded only there, one attempt per pass through a card (a lap of a looping card) collected by `AttemptPass` (`static/js/st/srs/attempt.js`) and graded by `static/js/st/srs/grade.js` (again/hard/good/easy from the raw counts it stores, `GRADE_ALGO`): a finished pass writes one review per measure plus one for a multi-measure card's range (with `bars`), under the drawer's hand (`itemHand`), except that a measure on the ladder whose rung isn't due (`onScheduleMeasures` in `planner.js`) is graded only when the pass fails it, else its pass goes to the totals (`MeasureCardGenerator#practiceOnly`, shared by free practice and the programme), so looping a card never climbs the ladder. After each pass played through in wait mode the generator's `caption()` gives its pace and stops (`passPace` in `attempt.js`, `paceCaption`: none without the score's rhythm on every column of the card, and cleared with the practice so a session never opens on the last one's), which the programme prefixes to when its measure returns. The page calls `takePractice` at Begin, Rest, page leave and drill rebuild (via `recordSession` and `componentDidUpdate`), which abandons the pass in progress: its totals and those of the rest of that card go through `recordSectionPractice`, never a graded review. The page tells the generator the mode (`setDrill`) and reports each further slip on a missed column (`NoteStats#slipNotes`, once per try) for the grade; a miss's hand comes from the `column.staves` of the notes it is blamed on (`NoteList#blamedNotes`) and `session.clefs` from `column.clefs` (`extractSectionColumns` with `notation`). A card takes any number of measures and the whole section option is one looping card, in both modes and on either renderer. Its section and card size are picked with `NumberPicker` (`static/js/st/components/number_picker.jsx`, the `measure` input type of `GeneratorSettings`), clamped to the piece with start and end dragging each other along (`sheetMusicSectionUpdate`). The generator learns progress without page changes: `NoteList#shift` calls `generator.columnDone`, and `addNoteListener` in `note_stats.js` reports hits and misses (a hit fires after its column's shift).
- The legacy staff (`static/js/st/components/staves.jsx`) draws every column as whole notes one column width apart (`staff_notes.jsx`, `components/staff/`), for the drills and for an imported piece the engine can't draw alike; its fixed pixel offsets are unscaled constants and CSS multiplied by `--staff-scale`, so size changes go through the `scale` prop, never per-element. `GrandStaff` puts each note on the staff whose clef leaves it fewest ledger steps (the middle C split). An imported piece's columns still carry the score's rhythm from `musicxml.js` and `extractSectionColumns` (`beat`, `notation`, `extras`; see `note_values.js`), which only the engine's join reads, and the score's ornaments as `allowed` (the grace notes of the column's notes, the neighbours of every trill, turn or mordent sounding at it, and a trill's own note after its onset as it keeps alternating; a wavy line trills every note under it; kept on each song note as `ornaments`, `trill` marking the alternating ones and `at` the beat one written on a tie's continuation sounds from, by the importer), which only the matcher reads; column copies keep those through `COLUMN_JOIN_KEYS` (`cardColumn`, `SheetMusicGenerator#nextNote`), and a column without them (pasted notation, a piece stored before song format 2) can't be joined, so the app staff draws it (a piece stored before song format 3 allows no ornaments until re-imported).
- The Staff page (`static/js/st/components/pages/sight_reading_page.jsx`) judges notes only between Begin and Rest; specs that play notes must press Begin (or call `beginSession()`) first. Every detection rule lives in the pure matcher `static/js/st/note_matcher.js`, which `onMidiMessage` feeds one note on or note off at a time, synchronously, with the event's `timeStamp`: it owns the keys down (`held`, kept across hits), the keys touched at the head column (`touched`, emptied at each hit and whenever another list takes over; a key in the head's `allowed` ornaments is held but never touched, required or a slip) and the head column itself, and tells the page each judgement as it makes it, before the list advance the ones after it describe (`judge` feeds every MIDI event through the matcher and renders what `applyEvent` collected in one update: the stats, the shake, the engine card's marks, the slider, and `heldNotes`/`touchedNotes` as a render mirror). Never judge a note in a `setState` callback again: presses batched into one render all saw the same head, which is how a MIDI packet crossing a column boundary used to give a false slip and stall. In notes mode only key-downs are judged: a release is never a miss and never resets the column (the pedal isn't read either), so a column completes once each of its keys has gone down since it became the head, however spread out, and its hit event carries that `spread` (first to last of its key-downs) for the grade to use later. The matcher looks one column either way on the events' timeStamps (a press without one, the on-screen keyboard, gets neither): a key of the next column is held early and credited to it when the head completes, chaining that column's completion too (the hit records it in `early`), unless the head takes longer than `EARLY_KEY_WINDOW` to complete, which makes it a slip on the head; a key of the column just completed struck again within `LATE_REPEAT_WINDOW` is ignored. Add or change a rule in the matcher and spec it in `static/js/spec/note_matcher_spec.js`; what stays on the page is the rest-vs-session, dropped-pitch (`droppedStaffNote`), `document.hidden` and chords `ignoreAbove` guards. The chord drill is the matcher's too, checked only on release (`chordHit`/`chordMiss`). `/` renders the legacy staves (`STAVES[].render`), `/staff2` renders `StaffTwo`, which lacks ledger lines and whose scrolling notes miss the scroll-mode hit zone, so it is not ready for `/`.

## Sharp edges

- Note names use scientific pitch notation like MusicXML and MIDI: middle C is `"C4"` = MIDI 60 (`MIDDLE_C_PITCH`), and LML notation writes it `c4`. Octave/pitch conversion lives only in `nameOctave`/`octavePitch` in `static/js/st/music.js`; `noteStaffOffset` rows are unchanged from the old numbering. Until 2026-09 the app named middle C `"C5"`: data from then (IndexedDB pieces before `DB_VERSION` 2, library files before `LIBRARY_VERSION` 2, the legacy deck, the old `st:sheet_music_deck` settings key) is renumbered on load with `shiftNoteOctave`/`shiftNotationOctaves`; new stored formats must never mix the two. The song editor's draft is marked `middleC: "c4"` (`readSongDraft`). The frontend no longer uses the server song library (`/songs`): nothing lists, loads or saves server songs, and the play-along editor keeps only its local draft; removing the library server-side belongs to the backend retirement.
- Measures of imported MusicXML use the score's printed bar numbers (`metadata.measureNumbers`; a leading pickup is measure 0), while notation-text songs number from 1; go through `measureBeatRange`/`measureNumberRange` in `static/js/st/song_sections.js` rather than indexing `measureStarts`.
- The old localStorage deck (`st:sheet_music_pieces:v1`) is migrated into the pieces store once; the `legacyDeckMigrated` record in the `meta` store stops it re-running, and the old key is left in place. Schema changes bump `DB_VERSION` with a new `upgradeSchema` step. A stored piece's song carries its own `SONG_FORMAT` (`sheet_music_deck.js`): older formats are read as they are and only gain what a re-import brings, so bump it and `LIBRARY_VERSION` rather than `DB_VERSION` when the song model grows.
- Drilled sheet music columns are note names drawn in the trainer's key signature, one column per onset: rhythm, ties and rests are never matched or scored, only drawn. While an imported piece is the generator, that key follows the score: the generator's `keySignature` (read through `scoreKeySignature` in `generators.js`) gives the score's key at the section's start measure (`metadata.measureKeySignatures`, raw fifths; keys outside -6..5 give none), the page applies it to state on mount and on every settings change without storing it; with no score key the score page draws in C major. A piece stored without per-measure keys has no score key until re-imported; re-importing the same score replaces that piece in place, keeping its id and stats (see `addPiece` in `sheet_music_deck.js`). When an import "doesn't match the score", compare the imported song model against the XML before touching the importer.
- Song beats are quarter notes everywhere (`beatsPerMeasure` for 6/8 is 3). `static/js/st/song_parser.js` is the reference for how notation becomes the `MultiTrackSong` model.
- Diatonic (7-step) scale notes are spelled by letter (`letterNoteName` in `static/js/st/music.js`), not by `noteName`'s pitch-based enharmonic guess, so each letter name appears exactly once (e.g. Gb major's degree is Cb, not B). Chords and the chromatic scale still use pitch-based spelling.
- `StaffTwo` (`static/js/st/components/staff_two.jsx`) paints its Two.js scene via `flush()`, gated by `this.flushChanges`. That flag is normally set by memoized watcher components (`RefreshNotes`/`RefreshStaves`) that only re-run on a prop *change* — so any code path that needs a repaint without a subsequent prop change (e.g. the post-mount flush in `componentDidMount`) must set `this.flushChanges` and call `this.flush()` directly. Don't assume asset refs or `state.two` exist yet: `renderStaves()` waits on `assetsReady()`, and `componentWillUnmount()` tolerates an unset `state.two`.
- First launch is gated behind `/welcome` (`static/js/st/components/pages/onboarding_page.jsx`): `HomeGate` in `static/js/st/components/app.jsx` redirects `/` there until the `st:onboarded:v1` localStorage flag (`static/js/st/onboarding.js`) is set, which both onboarding actions and `/setup`'s Begin do. An existing install (a saved `defaults:midiIn` or imported pieces) gets the flag set and isn't redirected.
